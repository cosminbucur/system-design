# Understanding Spring Cloud Sleuth

## What is Spring Cloud Sleuth?

**Spring Cloud Sleuth** is a distributed tracing library for Spring Boot applications. In a microservices architecture, a single user action can trigger a cascade of internal HTTP requests, database queries, and message queue events across multiple independent services. When an error occurs or a request slows down, debugging by looking at separate log files for each service becomes nearly impossible. 

Sleuth solves this by automatically injecting unique tracking identifiers into your logs and propagating them across network boundaries. 

*(Note: Spring Cloud Sleuth was officially active through Spring Boot 2.x. For Spring Boot 3.x and newer, its functionality has been succeeded by Micrometer Tracing, though the core concepts of traces, spans, and propagation remain identical.)*

---

## Core Concepts

1. **Trace ID**: A unique identifier assigned to the initial request. As the request travels through Service A, B, and C, this exact same Trace ID is carried along, allowing you to stitch together the entire end-to-end lifecycle of that request.
2. **Span ID**: Represents a basic unit of work or a single operation within a trace (e.g., an incoming HTTP request, an outgoing database call, or a message publish). Every time a service calls another service, a new child span is created with its own Span ID, while retaining the parent's Trace ID.
3. **Baggage**: Key-value data that gets passed along ("propagated") alongside the trace across all participating services, allowing you to carry contextual business data (like tenant IDs or user roles) through the call graph.

---

## How Sleuth Works Under the Hood

* **Automatic Instrumentation**: Sleuth hooks into standard libraries (`RestTemplate`, `WebClient`, `Feign`, Spring MVC, Spring WebFlux, Kafka, and messaging channels) via libraries like Brave. When a request enters Service A, Sleuth checks incoming headers for a Trace ID. If none exists (e.g., call from a frontend client), it generates a new one. If it makes an outgoing call to Service B, Sleuth automatically injects the Trace ID and current Span ID into the HTTP headers (e.g., `X-B3-TraceId`, `X-B3-SpanId`).
* **Log Correlation**: Sleuth integrates natively with SLF4J and Logback. It automatically appends trace metadata to your logging Diagnostic Context (MDC) so that every log statement prints in a format like:
  ```text
  [Service-Name, TraceID, SpanID, Exportable]
  ```
  This lets you run a simple command like `grep [TraceID]` across your log aggregation tool (like ELK or Grafana Loki) to instantly see every single log line generated by that specific transaction across all microservices.

---

## Real-Life Usage Scenario

Imagine an **E-Commerce Platform**:
1. A customer places an order via the **API Gateway**.
2. The Gateway calls the **Order Service** to record the purchase.
3. The Order Service calls the **Payment Service** to process credit card details.
4. Concurrently, it pushes an event to **RabbitMQ** for the **Inventory Service** to reserve stock and the **Notification Service** to send an email.

Without distributed tracing, tracking down why an order failed midway is a nightmare. With Sleuth:
* A single **Trace ID** links the initial API Gateway call all the way down to the database updates and message queue handlers.
* Visualizers like **Zipkin** or **Jaeger** render this as a clean, waterfall-style timeline showing exactly where time was spent or where an exception was thrown.

## Code Samples

### 1. Maven Dependencies (Spring Boot 2.x)
To enable Sleuth and export traces to a UI visualizer like Zipkin, add these dependencies to your `pom.xml`:

```xml
<dependencies>
    <!-- Spring Boot Web -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>

    <!-- Spring Cloud Sleuth -->
    <dependency>
        <groupId>org.springframework.cloud</groupId>
        <artifactId>spring-cloud-starter-sleuth</artifactId>
    </dependency>

    <!-- Zipkin Reporter (Sends traces to Zipkin server) -->
    <dependency>
        <groupId>org.springframework.cloud</groupId>
        <artifactId>spring-cloud-sleuth-zipkin</artifactId>
    </dependency>
</dependencies>
```

### 2. Application Configuration (`application.yml`)
Configure your service name and the sampling rate (setting it to `1.0` means 100% of requests are traced, which is great for development):

```yaml
spring:
  application:
    name: order-service
  sleuth:
    sampler:
      probability: 1.0 # Sample 100% of requests for tracing
zipkin:
  base-url: http://localhost:9411 # Local Zipkin server URL
```

### 3. Service-to-Service Communication Code
Because Sleuth auto-configures Spring's `RestTemplate` or `WebClient` beans, context propagation happens completely transparently without writing boilerplate header-injection logic:

```java
package com.example.orderservice;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.client.RestTemplate;

@Configuration
class AppConfig {
    @Bean
    public RestTemplate restTemplate() {
        return new RestTemplate(); // Sleuth instruments this bean automatically
    }
}

@RestController
public class OrderController {

    private static final Logger log = LoggerFactory.getLogger(OrderController.class);
    private final RestTemplate restTemplate;

    public OrderController(RestTemplate restTemplate) {
        this.restTemplate = restTemplate;
    }

    @GetMapping("/orders/{id}")
    public String processOrder(@PathVariable String id) {
        log.info("Received request to process order: {}", id);

        // When making this call, Sleuth automatically injects Trace and Span IDs into HTTP headers
        String paymentResponse = restTemplate.getForObject(
            "http://localhost:8082/payments/charge/" + id, 
            String.class
        );

        log.info("Payment service responded with: {}", paymentResponse);
        return "Order " + id + " processed successfully! Status: " + paymentResponse;
    }
}
```

### What your logs will look like:
When you hit `/orders/123`, your console logs will automatically look like this, allowing instant correlation across microservices:

```text
2026-10-04 14:15:22.101  INFO [order-service,48bf92f8149e29f1,48bf92f8149e29f1] 12345 --- [nio-8081-exec-1] c.e.o.OrderController : Received request to process order: 123
2026-10-04 14:15:22.450  INFO [order-service,48bf92f8149e29f1,72bfa12b934c10a3] 12345 --- [nio-8081-exec-1] c.e.o.OrderController : Payment service responded with: SUCCESS
```
*(Notice how `48bf92f8149e29f1` is the **Trace ID** that stays constant, while the third token changes from request entry to downstream processing, marking different **Span IDs**).*
